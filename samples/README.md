# Sample and test data

Everything in this folder is **synthetic**. It exists so the dashboard can be
developed and tested without spending API credits, and without using a real
person's resume.

Two harnesses run from the browser console, and neither needs an API key:
[`harness.js`](#replaying-the-cases) checks the board and resume tailoring, and
[`jobs-harness.js`](#jobs-harnessjs) checks the All openings list and the two
Search deeper steps, ranking the openings and searching the web.

## `sample-resume-jordan-kim.pdf`

A fictional resume used to exercise the upload flow end to end, and the person
the default board is scored for: the header, the sample positioning line and
the profile menu's "Sample board (Jordan Kim)" entry all describe this made-up
candidate. Jordan Kim does not exist. The employers named in it are real
companies, but the roles, dates and accomplishments are invented.

Use it to try the Upload a resume button without uploading your own resume.

## `test-fixtures/`

Deliberately awkward inputs used to test the file reader:

| File | What it tests |
| --- | --- |
| `alex-morgan.docx` | Word extraction, including tabs, line breaks and XML entities |
| `broken.docx` | A `.docx` with no `word/document.xml`, which must produce a clear error |
| `plain-resume.txt` | The plain-text path |
| `tiny.txt` | A file too short to be a resume, which must be rejected |

## `resumes/*.txt`

Twelve fictional resumes, none of them anything like the sample candidate's, for
testing the upload flow end to end against the real API. Each is a person the
board was not built for, which is the point: the tailoring has to work for them
too, and for most of them the right answer is "this board is the wrong board,
here are employers in your field".

| File | Who | What the board should do |
| --- | --- | --- |
| `nurse-slc.txt` | An ICU nurse in Salt Lake City staying in nursing | Field mismatch: suggested health systems lead the page |
| `austin-cs-ms.txt` | A CS master's student in Austin with an ML focus | Geography re-maps; degree bars are no obstacle |
| `denver-career-changer.txt` | A six-year teacher in Denver with a 2026 analytics master's | Six years count; new-grad programs are the wrong cohort |
| `byu-accounting-it-audit.txt` | A BYU accounting senior in Provo on the IT-audit track | Local mode, no suggestions, but no University of Utah extras |
| `bootcamp-remote.txt` | A bootcamp graduate in rural Montana, no degree, remote only | Remote-first mode |
| `experienced-de-slc.txt` | A five-year data engineer in Salt Lake City | Over-qualified: the seniority cap never fires |
| `mech-engineer-logan.txt` | A Utah State mechanical engineering senior relocating to Salt Lake | Field mismatch: aerospace and manufacturing employers lead |
| `chemistry-lab-slc.txt` | A University of Utah chemistry senior, two years of bench work | Field mismatch with the Utes extras shown: labs and diagnostics lead |
| `journalism-denver.txt` | A CU Boulder journalism graduate in Denver | Field mismatch and re-mapped geography: newsrooms lead |
| `ux-designer-slc.txt` | A Weber State design BFA in Ogden heading for product design | Adjacent to the board's product roles; Utah design employers added |
| `marketing-analytics-boise.txt` | A Boise marketing coordinator one year in, moving toward analytics | One year counts; Boise and remote employers added |
| `civil-engineer-intl-phoenix.txt` | An international civil-engineering master's student in Phoenix | Field mismatch; programs that refuse sponsorship are the wrong cohort |

Every name, employer history and date is invented. Tailoring the board to one
of them costs about $0.30 on the default model and effort (Sonnet 5.5, high).

The upload dialog also ticks two further steps by default: "Rank every opening
in the database for this person" and "Search the web for openings the database
does not have", set to Deep. They are billed on top of the $0.30. Neither has
been run against the live API, so their cost is an estimate: on Sonnet 5.5,
about $0.50 for the ranking and a few dollars for a Deep search. Untick both to
test tailoring alone, and trust the completion toast, which reports what the
run actually cost.

## `cases/*.json`

Fifteen mock API responses, generated by `make-cases.py` from the board itself so
they always cover every employer, 82 today (the page rejects a response that
covers fewer than 80% of them, which is how the previous hand-written cases died
when the board grew). Twelve are what Claude would plausibly return for the
twelve resumes above; three exercise the page's defences:

| File | What it covers |
| --- | --- |
| `nurse-slc.json` … `civil-engineer-intl-phoenix.json` | One per resume above, with scores set by simple rules per persona and suggested employers from the resume's own field and city |
| `hostile-output.json` | Out-of-range scores, unknown and duplicate employers, bad enum values, a suggestion that is really a board employer, 25 suggestions (the page keeps 20), over-long strings, a `javascript:` LinkedIn URL |
| `too-few-companies.json` | The first 70% of the board (57 of 82 employers today), which the page must reject |
| `profile-predates-employers.json` | A profile made before two employers joined the board, which must hide them and say so |

Re-run the generator after adding an employer:

```bash
python3 samples/make-cases.py
```

> **These are fabricated fixtures, not career advice.** The suggested employers
> in them are real companies, but the hiring programs, application windows and
> job titles were written to look plausible for testing. Do not rely on any
> claim in these files. Only a real run against the Claude API produces output
> intended to be acted on, and even then the suggested employers are explicitly
> marked unverified.

### Replaying the cases

`harness.js` replays every case through the page and checks the rules LOGIC.md
promises: the 80% rule, the seniority cap, eight Tier 1 cards, badge
derivation, suggested employers (deduplication, the twenty cap, when they lead
the page), geography relabeling and local mode, the University of Utah extras,
hidden chips, the New this week count and tags, hidden untailored employers,
stale profiles after a newer refresh, and what the page does with hostile
output. The checks are written from the documentation, not copied from the code.

Two of those are easy to misread after the 2026-10-09 changes:

- **New this week.** On the board, "new" means added in the six days up to the
  latest refresh and not yet past its closing date. It is measured from the
  refresh date, not from today, so a mid-week refresh keeps the tags the last
  one set and a refresh a week later clears them. The harness recomputes the
  count from that rule.
- **The University of Utah extras** are the career-fair strip, the "Hires from
  the U" chip in the Utes filter row, and the alumni bonus. They follow the
  resume, and have nothing to do with the University of Utah's own employer
  card, which joined the board on 2026-10-09.

Serve the folder, open the page, and run this in the browser console:

```js
await import('/samples/harness.js'); await JobFinderHarness.run();
```

It prints a table of every check and restores whatever profile was active. No
API key, nothing spent. On today's 82-employer board that is about 510 checks.
The number moves with the board, because some checks apply only when a case
gives them something to check, such as an employer with no openings.

To replay one case by hand:

```js
const data = await (await fetch('/samples/cases/austin-cs-ms.json')).json();
const T = window.JobFinderTailor;
const profile = T.buildProfile(data, {
  model: 'claude-sonnet-5-5', effort: 'high',
  usage: { input_tokens: 3000, output_tokens: 20000 }, servedBy: 'claude-sonnet-5-5',
});
T.applyProfile(profile);          // T.applyProfile(null) restores the built-in board
```

## `jobs-harness.js`

`jobs-harness.js` checks the parts of the page that look past the hand-picked
board: the All openings list, Claude's ranking of the openings, and the web
search that saves what it finds. The last two are the Search deeper steps.

Serve the folder, open the page, and run this in the browser console:

```js
await import('/samples/jobs-harness.js'); await JobFinderJobsHarness.run();
```

It prints a table of every check beside its group, then one line saying how
many passed. No API key, nothing spent: the harness never contacts
api.anthropic.com.

There are 84 checks in 14 groups. The group names are the file's own:

| Group | Checks | What it covers |
| --- | --- | --- |
| `key` | 5 | One posting has one key however it is linked: a Greenhouse id, a Workday requisition with or without a locale or a repost suffix, an id carried in the link. Any other link is keyed on host and path, ignoring tracking parameters and a trailing slash but keeping a job id that sits in the query string |
| `merge` | 6 | One list from the feeds and the board: a posting on both is listed once and the hand-read facts win; a feed row from a differently named source of the same employer lands on that employer's card; rows with no link or no title are ignored; an employer with no card is a feed-only source; `feedExtras` lists what a feed has beyond the hand-read openings |
| `dead` | 3 | A board link the feeds report dead is marked gone and treated as closed, is left out of the list, and is tagged "no longer posted" on its card rather than shown as live |
| `cards` | 3 | A card offers the rest of its employer's feed; clicking that button opens All openings on that employer alone; the employer chip clears the filter |
| `new` | 3 | Posted, or first seen, within seven days of the database's refresh date is new; posted long before the refresh, or dated after it, is not; a posting past its closing date is closed, never new |
| `filter` | 9 | Closed postings never pass; Where, Level, Field and Source each narrow the list; Out of reach hides a posting two or more years beyond the candidate; Weak fits hides software ladders and degree bars; New this week keeps only new postings; the search box matches title, employer and place |
| `classes` | 6 | Experienced-level titles and internal-only postings are left out of the default list; the Experienced chip and the Internal only chip each list their own class alone; a search reaches experienced titles but not internal-only postings; an experienced title with no years stated counts as four years away; neither class is sent to Claude for a new graduate |
| `leads` | 4 | A state job bank row is its own source, not an employer feed; it is tagged as a lead and offers a search for the employer's own posting; once the real posting is found on the web the lead gives way to it, and it comes back when that find is removed |
| `order` | 3 | Until Claude ranks, order is a plain keyword match: the same job scores lower when its posting asks for three more years, a local job outranks the same job far away, and no row carries a score from Claude |
| `rank` | 7 | The list sent to Claude is every listed opening, closed ones left out, in a fixed order, one JSON line each; the request asks for structured output with adaptive thinking and caches the list; unknown ids, repeats and junk in the reply are dropped, scores are clamped to 60-100 and text is capped; a reply that is not a ranking yields nothing rather than an error; the seniority ceiling applies to a single job (three years short tops out at 70, two at 80); ranked openings sort above unranked ones |
| `search` | 8 | The web search request carries web search, page reading and the save tool, capped at the chosen depth; searches are biased to the candidate's city and the brief carries no name; Claude is told which employers the database already reads, and a job bank lead does not count as read; the search starts from the employers the board could not read, with their links, and from the job bank leads that suit the candidate; a link that is not http is never passed on; a name Claude wrote into a tailored profile's positioning line is taken out of the brief, while a longer word that only starts with the name is left alone; the save tool requires every field and refuses extra ones; depths scale the budget |
| `save` | 8 | What the save tool accepts: a posting found and opened in the session is saved; a link that is not http, a listing site, a link never seen in the session and a missing title are rejected with reasons; a repeat, or a job the board already has, is turned away as known; a link seen in results but never opened is saved and flagged as not opened; scores are clamped and only well-formed dates are kept; place is read as home, remote or elsewhere; a link identified by its query string must match the one that was seen, though a longer path to the same page is fine; a malformed call gets an error, not a crash |
| `loop` | 11 | The search loop, run against the stand-in: a paused turn is sent back as it is; each save call is answered with what was saved and what was rejected; a tool that does not exist is refused; the tally counts saves, searches and page reads and keeps the closing summary; progress is reported in plain words; what was saved lands in the browser's own database under its profile; a refusal ends the run and says so; a cut-off reply is never acted on; a run that overshoots its budget is stopped; an API error is passed to the caller; clearing a profile's finds empties it |
| `restore` | 1 | The real database is back: it carries its own date again and none of the invented rows is left in the list |

The `new` group checks the rule for the All openings list, which is seven days.
The board's own rule, six days up to the latest refresh, is checked by
`harness.js` above.

### What it swaps in, and what it puts back

While it runs, the harness replaces two things:

- **The openings database.** The page's copy of `jobs.json` is swapped for a
  small invented one: made-up employers such as "Wasatch Ledger Co-op" and
  "Canyon Grid Power", links on `example.test`, and a refresh date of
  2031-03-10, because "new" is measured from the database's date and not from
  the clock. The file on disk is not touched. To test merging and dead links it
  also attaches two rows to the first employer on the board that has a live
  opening and reports one link of the second as dead, so those two real
  employers' cards change while it runs.
- **The API.** The harness builds the ranking and search requests and inspects
  them without sending them. It hands the ranking and save functions replies it
  wrote itself, and runs the search loop against a stand-in client that replays
  a script: a paused turn, a save call, a call to a tool that does not exist, a
  refusal, a cut-off reply, a run that overshoots its budget, and an API error.

When it finishes it fetches the real `jobs.json` again and puts back the saved
ranking, the list's filters and whichever tab the page had remembered. The web
finds it saves go under a profile id of its own, `harness`, which it clears.
One test find is added to the sample board's finds and removed again.

It does not put a tailored profile back. The harness switches to the built-in
sample board before it starts and leaves the page there. Saved profiles are not
touched, so choose yours again from the profile menu in the header.

Four smaller things are also left changed. The search box is emptied. A Where
chip that was on in the Employers tab is switched off, as it is whenever a
profile is applied. On the All openings tab, a filter chip that was on still
filters the list but loses its highlight, and the Sort menu reads Best match
while the list keeps the order you had chosen, so click Reset there to start
clean.

### What a pass does not show

A pass shows that the page builds the requests it should and treats every reply
as untrusted. It does not show what the live API returns. Neither Search deeper
step has been run against the live API, only against this stand-in, so the cost
figures for those two steps are estimates and the completion toast is the real
number.

The harness also leaves out the dialog around those steps: loading the SDK,
streaming a real reply, and the messages for a rejected key or a rate limit.

The `restore` check is weaker than it looks. If the browser already held a
saved ranking when the harness started, that check passes without testing
anything. It only means something in a browser where Claude has not yet ranked
the openings.
